## Difficulties

1. **The shared contract changed during the sprint.** Refresh, logout and `resendMfa` were added after the layered baseline (the MFA operations were already in the contract). Every new variant has to implement the extended contract with the same behavior and the same errors.
2. **The cost of MFA (change request CR2) cannot be measured on the layered variant.** It was implemented in the same commit as the refresh/logout changes and the interactive demo, so the history cannot give a clean change-impact measurement for it. New variants will therefore implement the base `AuthService` first, without MFA, and get MFA in a separate pull request.
3. **The interactive demo stopped with an exception on invalid input** (short password, empty username, empty MFA code). Fixed in this milestone.

## Known limitations found in the M1 review

Each item below was reproduced against the current code.

| Area | Observation | Why it matters for the study |
|---|---|---|
| Memory | Revoked access tokens are never removed (1,000 refreshes leave 1,000 entries), and expired or abandoned MFA challenges stay in memory (500 abandoned logins leave 500 entries, also after an hour). | Long benchmark runs would measure ever-growing maps. Needs a cleanup rule, or a bounded workload, before the M2 measurements. |
| MFA | There is no limit on wrong codes (100,000 wrong codes were rejected and the correct code was still accepted afterwards), and `resendMfa` keeps the same challenge alive indefinitely. `AuthFailure.RATE_LIMITED` exists but is not used. | Security limitation; whatever rule is chosen must be implemented identically in every variant. |
| Logout | With a valid access token and an unknown refresh token, `logout` throws nothing and revokes only the access token; the session's refresh token still works. The contract says logout invalidates both credentials. | The expected behavior should be settled in `auth-api` before the contract tests are written. |
| Login timing | For an unknown username the password hash is not computed, so the response is faster than for a wrong password. | Can reveal whether a username exists; also makes "unknown user" and "wrong password" different workloads in benchmarks. |
| Password hashing | `Sha256SaltedHasher` is a single salted SHA-256. The original plan kept cryptography simple on purpose, which suits an architecture study: the hash is fast, so architectural overhead stays visible in login latency. With PBKDF2 or bcrypt, hashing would dominate login latency. | Use the same hasher in every variant, and report login separately from operations that do not hash (`verify`, `refresh`). |

Still to decide before the measurements:

- the JMH workload (operation mix, number of users) and the thread counts;
- how the implementation time of each change request is recorded;
- the order in which a change request is applied to the variants: the same person gets faster with each repetition, so the order should be recorded and discussed as a threat to validity.

Proposed tools (to be confirmed): JMH for latency distribution and throughput; JaCoCo for test coverage; a static metrics tool such as CK for coupling and complexity; `git diff --numstat` per change-request pull request for changed files and lines.
